# MongoDB 인덱스 운영 절차

이 문서는 `scripts/mongo/indexes`의 v001 인덱스 마이그레이션을 실제 MongoDB에 적용하는 절차입니다. 모든 명령은 저장소 루트에서 실행합니다.

애플리케이션 시작 시 인덱스를 자동 생성하지 않습니다. 운영 데이터의 중복을 자동으로 제거하거나 기존 인덱스를 자동으로 삭제하지도 않습니다. 사전 점검에서 중복 또는 호환되지 않는 인덱스가 발견되면 원인을 확인하고 별도 변경 계획을 승인받은 뒤 다시 시작합니다.

V001은 무결성을 보장하는 unique index 11개와 실제 조회를 지원하는 non-unique index 2개를 관리합니다. MongoDB 기본 `_id_` index와 예상하지 못한 기존 index는 변경하지 않습니다.

## 적용 전 준비

다음을 모두 확인합니다.

- 대상 DB의 최신 백업과 복구 절차가 준비되어 있습니다.
- 인덱스 생성 부하를 줄일 수 있는 저트래픽 시간대를 확보했습니다.
- 사전 점검 계정에는 대상 컬렉션과 인덱스 조회 권한이 있습니다.
- 적용 계정에는 필요한 컬렉션·인덱스 생성과 `_aandi_schema_migrations` 기록 권한이 있습니다.
- URI가 가리키는 DB와 `MONGO_INDEX_EXPECTED_DATABASE`가 정확히 일치합니다.

대상 환경 값을 설정합니다. URI의 DB 이름과 예상 DB 이름은 예시를 실제 값으로 바꿉니다.

```sh
export MONGODB_URI='mongodb://USER:PASSWORD@HOST:27017/aandi?authSource=admin'
export MONGO_INDEX_EXPECTED_DATABASE='aandi'
```

URI에는 비밀 정보가 포함될 수 있으므로 셸 기록, CI 로그, 문서에 실제 값을 남기지 않습니다.

## 1. 사전 점검

읽기 전용 사전 점검을 실행합니다.

```sh
mongosh "$MONGODB_URI" --quiet --file scripts/mongo/indexes/v001-preflight.js
```

사전 점검은 고유 인덱스 대상의 중복 데이터, unique key의 BSON 타입, 기존 인덱스의 키·옵션 호환성을 확인합니다. 배열을 포함한 예상 밖 타입은 multikey 중복을 놓치지 않도록 적용 전에 차단합니다. 실패하면 적용하지 않습니다. 출력에는 중복 키 원문 대신 표본 그룹 수와 그룹별 문서 수만 포함되며, 이 스크립트는 데이터를 수정하지 않습니다.

## 2. 적용 승인

다음 항목을 검토하고 운영 승인 기록을 남깁니다.

- 사전 점검이 오류 없이 완료되었습니다.
- 백업 시각과 복구 담당자가 확인되었습니다.
- 대상 DB 이름과 접속 환경을 재확인했습니다.
- 저트래픽 적용 시간과 모니터링 담당자가 정해졌습니다.
- 발견된 중복이나 비호환 인덱스가 없습니다.

하나라도 충족하지 않으면 적용을 중단합니다.

## 3. 적용

적용 명령에만 일회성 확인 토큰을 전달합니다.

```sh
MONGO_INDEX_APPLY=YES mongosh "$MONGODB_URI" --quiet --file scripts/mongo/indexes/v001-apply.js
```

`v001-apply.js`는 변경 전에 전체 사전 점검을 다시 수행합니다. `MONGO_INDEX_EXPECTED_DATABASE`가 실제 DB와 다르거나 `MONGO_INDEX_APPLY=YES`가 없으면 변경하지 않고 실패합니다. 호환되는 기존 인덱스는 이름이 달라도 유지하고 누락된 인덱스만 생성하며, 모든 인덱스가 성공한 뒤에만 `_aandi_schema_migrations`에 완료 표식을 기록합니다.

중간에 실패하면 자동 삭제나 자동 중복 제거를 시도하지 않습니다. 실패 원인을 해결한 뒤 사전 점검부터 다시 수행합니다.

## 4. 적용 후 검증

읽기 전용 검증을 실행합니다.

```sh
mongosh "$MONGODB_URI" --quiet --file scripts/mongo/indexes/v001-verify.js
```

검증은 필요한 인덱스의 키와 옵션이 실제 DB에 존재하는지 확인합니다. 성공한 뒤 애플리케이션의 오류율과 MongoDB 인덱스 생성 부하를 관찰하고 운영 기록에 결과를 남깁니다.

과제 생성·수정·복사의 동시 CourseWeek 생성 수렴은 `ux_course_week(courseId, weekNo)` unique index가 실제 적용된 환경을 전제로 합니다. 이 인덱스가 없으면 애플리케이션의 충돌 후 재조회 로직만으로 중복 주차 생성을 막을 수 없습니다.

## 재실행과 복구 원칙

- 사전 점검과 검증은 읽기 전용이므로 반복 실행할 수 있습니다.
- 적용 스크립트도 호환되는 기존 인덱스를 다시 만들지 않도록 설계되어 있습니다. 재실행할 때도 반드시 사전 점검과 승인 절차를 반복합니다.
- 적용 완료 표식은 모든 인덱스 생성이 끝난 뒤에만 기록됩니다. 표식이 없으면 부분 적용 여부를 검증한 뒤 다시 실행합니다.
- 스크립트는 기존 인덱스를 삭제하거나 데이터를 합치고 삭제하지 않습니다. 롤백 또는 데이터 정리가 필요하면 별도 승인된 작업 계획으로 수행합니다.
- 인덱스 생성 자체를 되돌려야 할 때는 사용 여부와 쿼리 영향을 확인한 별도 변경으로 진행합니다. 이 절차에 자동 롤백은 없습니다.

## 로컬 및 CI 검증 범위

스크립트 문법과 단위 테스트는 다음 명령으로 확인할 수 있습니다.

```sh
find scripts/mongo/indexes -name '*.js' -print0 | xargs -0 -n1 node --check
node --test scripts/mongo/indexes/v001-index-lib.test.js
```

CI도 같은 정적 검사와 단위 테스트만 실행합니다. 로컬 및 CI 테스트는 실제 MongoDB에 접속하거나 운영 데이터, 권한, 현재 인덱스 상태를 검증하지 않습니다. 실제 환경 검증은 해당 DB에 대해 `preflight -> 승인 -> apply -> verify` 순서로 수행해야 합니다.
