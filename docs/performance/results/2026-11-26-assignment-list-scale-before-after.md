# 과제 목록 재측정 결과 (2026-11-26)

과제 목록이 과제마다 하위 데이터를 따로 조회하던 서버(이전)와 일괄 조회하는 서버(현재)를 과제 30·300·1,000개 데이터로 다시 쟀습니다. 과제가 많을수록 차이가 커졌고, 이전 서버가 버티지 못한 50 RPS를 현재 서버는 누락 없이 처리했습니다.

## 이전과 현재

| 조건 | 이전 | 현재 | 변화 |
| --- | --- | --- | --- |
| 과제 30개 · 100 RPS, P95 | 10.160ms | 10.373ms | 2.10% 증가, 편차 범위 안 |
| 과제 300개 · 15 RPS, P95 | 79.049ms | 47.760ms | 39.58% 감소 |
| 과제 1,000개 · 5 RPS, P95 | 187.474ms | 128.437ms | 31.49% 감소 |

| 과제 1,000개 · 50 RPS | 처리량 8.609 req/s, 요청 누락 4,833 | 처리량 49.940 req/s, 누락 0 | 목표 부하 유지 |

모두 3회 측정의 중앙값입니다. 15·5 RPS 비교는 이전 서버 3회 중 가장 좋은 값도 현재 서버 3회 중 가장 나쁜 값보다 느려, 범위가 겹치지 않습니다. 로컬 MongoDB와 localhost API만 대상으로 한 값이며 운영 최대 처리량이 아닙니다.

## 측정 조건

| 항목 | 값 |
| --- | --- |
| API | `GET /v2/courses/{courseSlug}/assignments?status=PUBLISHED` (목록만) |
| 부하 | constant-arrival-rate, 2분 × 3회, preAllocatedVUs 30, maxVUs 200 |
| 데이터 | 과제 수만 다르고 생성 방식은 같음. 이전·현재가 같은 데이터인지 지문으로 확인 |
| 서버 | `./gradlew bootRun`, OpenJDK 21.0.6 |
| 저장소 | MongoDB 7.0.16 새 컨테이너 |
| 부하 도구 | k6 v0.52.0 공식 바이너리 (체크섬 확인) |
| 장비 | Apple M5 Pro, 48GiB, AC 전원, 측정 중 다른 빌드 없음 |

HTTP 실패율이 0보다 크거나, check가 100% 미만이거나, 요청 누락이 있으면 그 측정은 무효로 봅니다.

## 부하를 정한 과정

1. 과제 300·1,000개에서 이전 서버를 100 RPS로 30초 예비 실행하니 요청이 누락돼, 본 측정을 50 RPS로 낮췄습니다.
2. 50 RPS에서도 이전 서버는 처리량이 30.8·8.6 req/s에 그치고 요청이 누락됐습니다. 이 상태의 응답 시간은 대기열이 쌓인 값이라 응답 시간 개선율로 쓰지 않습니다.
3. 그래서 이전 서버가 누락 없이 버티는 부하(300개 15 RPS, 1,000개 5 RPS)를 예비 실행으로 찾고, 같은 부하로 두 서버를 다시 쟀습니다. 위 표의 P95 비교가 이 결과입니다.
